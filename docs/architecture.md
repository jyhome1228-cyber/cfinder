# 개발 구조

## 제품의 중심

C-Finder의 중심은 진로검사입니다. 개인 사용자는 검사 선택부터 응답·검토·결과로 이어지는 흐름을 이용합니다. 기관은 같은 검사 경험을 기관명, 로고, 색상, 운영 방식에 맞게 제공하는 형태로 확장합니다.

현재는 정적 HTML/CSS와 브라우저 ES 모듈로 구성합니다. 별도 프레임워크나 빌드 과정 없이 검사 흐름을 검토하고, 승인된 문항·채점 API를 나중에 연결할 수 있도록 책임을 나눴습니다.

## 모듈 경계

| 모듈 | 맡는 일 | 다음 연결 지점 |
| --- | --- | --- |
| `data/assessments.js` | 버전이 있는 체험 검사 정의와 문항 | 승인된 검사 정의를 가져오는 API |
| `core/assessment.js` | 응답 유효성, 상태 변경, 복원, 완료 조건 | 같은 계약에 대한 서버 재검증 |
| `core/storage.js` | 탭 내 임시 저장과 메모리 대체 | 인증된 응답 저장·불러오기 API |
| `core/router.js` | URL 해시 해석과 이동 | 필요한 경우 실제 서버 경로와 연결 |
| `services/results.js` | 완료 상태와 결과 응답의 경계 | 승인된 서버 채점·결과 조회 API |
| `config/tenants.js` | 기관 화면의 이름·문구·색상 | 서버에서 확인한 기관 설정 |
| `ui/home.js`, `home.css` | 메인 페이지와 영역 소개 탭 | 승인된 서비스 소개·결과지 콘텐츠 |
| `ui/`, `app.js` | 화면과 사용자 동작을 연결 | 저장 중·오류·재시도 등 서버 통신 상태 |

문항 데이터는 화면 파일에 넣지 않습니다. 화면에서 임의로 점수를 계산하지 않으며, 결과 제공 모듈도 현재 체험 응답으로 개인 유형을 만들지 않습니다.

## 화면과 글씨 기준

`styles.css`의 `--font-*` 변수가 공통 제목·본문·보조 문구 크기를 관리하고 `home.css`도 같은 변수를 사용합니다. 620px 이하와 360px 이하에서 제목 크기를 조정하지만 본문과 보조 문구를 함께 축소하지 않습니다. 주요 설명은 15~16px, 상태와 안내는 최소 14px를 유지합니다. 이 수치는 기본 글씨 16px 기준이며 `rem` 단위로 확대 설정에 따라 조절됩니다.

모바일 결과지 안내는 한 열로 배치하고, 응답 검토의 질문은 전체 너비를 사용합니다. 완료 버튼은 화면과 DOM 순서를 일치시키며, 다시 시작은 기본 `<dialog>`로 확인합니다. 변경 기준과 실제 검수 범위는 [1차 완료 보고](phase1-review.md)에 기록합니다.

## 응답의 생명주기

1. 학년에 맞는 검사 정의를 선택하고 새 응답을 생성합니다.
2. 응답 값이 해당 문항과 척도에 속하는지 확인한 뒤 새 상태를 저장합니다.
3. 이전·다음 이동과 검토 화면 수정에서도 이미 작성한 다른 응답을 보존합니다.
4. 모든 문항에 유효한 응답이 있을 때만 `completed`로 전환합니다.
5. 완료한 응답은 읽기 전용입니다. 재검사는 새 상태를 생성합니다.

이어하기는 첫 미응답 문항으로 이동합니다. 모두 응답했으면 검토 화면, 완료했으면 완료 화면으로 이동합니다. 진행 상태 복원 시 기관·검사·버전·학년이 맞지 않는 데이터는 사용하지 않습니다. 모르는 문항 ID나 잘못된 응답 값은 제거합니다.

## URL과 브라우저 이동 기록

검사 흐름의 해시 경로에는 `grade=middle` 또는 `grade=high`를 붙입니다. 예를 들어 `#test/0?grade=middle`은 중학생용 첫 문항이고, `#test/0?from=review&grade=middle`은 검토 화면에서 해당 문항을 수정하는 경로입니다.

`withGrade()`가 경로에 학교급을 기록합니다. 뒤로 가기·앞으로 가기로 이전 경로를 열 때는 그 경로의 학교급을 먼저 복원한 뒤 해당 응답을 화면에 연결합니다. 중학생용에서 고등학생용으로 전환해도 이전 이동 기록이 다른 검사의 응답에 연결되지 않게 합니다.

학교급이 없는 기존 해시 경로는 현재 선택한 검사로 해석한 뒤 `grade`를 추가합니다. URL에는 학교급·화면·문항 위치만 담으며 실제 응답은 저장 모듈에서 불러옵니다. URL을 다른 브라우저에 전달해도 응답이 함께 전달되는 것은 아닙니다.

## 저장 범위

현재 저장 키는 스키마 버전, 기관 ID, 검사 ID, 검사 버전, 학년을 포함합니다. 중학생용과 고등학생용을 오가거나 기관 예시를 열어도 각각의 진행 상태를 구분합니다.

`sessionStorage`는 같은 브라우저 탭의 새로고침을 지원하기 위한 임시 저장입니다. 다른 기기에서 이어하기, 계정별 검사 이력, 기관의 학생 응답 조회를 제공하지 않습니다. 저장 접근이 실패하면 메모리에서 현재 상태를 유지하고 화면에 저장 한계를 안내합니다. 탭 저장은 보안상 기관 데이터 격리를 보장하는 수단이 아닙니다.

## 기관별 설정

`resolveTenant()`는 등록된 설정만 선택하며, 알 수 없는 `org` 값은 기본 설정으로 돌아갑니다. `?org=sample`은 가상의 기관 화면 예시입니다. 검사 문항과 진행 로직은 기본 서비스와 공유합니다.

실제 기관용 서비스에서는 서버가 로그인한 사용자의 기관 소속과 권한을 확인해야 합니다. URL 파라미터나 브라우저 저장 값으로 기관 접근 권한을 결정하지 않습니다. 기관 생성, 검사 배포, 학생·상담자·운영자 권한, 집단 통계는 해당 서버 구조를 갖춘 뒤 연결합니다.

## 배포와 검증

정적 파일은 상대 경로, 화면 이동은 해시 경로를 사용합니다. GitHub Pages의 프로젝트 하위 경로에서도 직접 새로고침할 수 있는 구성입니다. Pages 활성화와 실제 배포 성공 여부는 별도로 확인합니다.

`npm run check`와 `npm test`는 통과했습니다. 상태 모듈 테스트는 잘못된 답변, 미응답 완료, 다른 기관·버전의 상태 복원, 완료 후 수정처럼 결과 신뢰성에 영향을 주는 경계를 확인합니다. 이 자동 검사는 실제 브라우저 화면 검증을 대신하지 않습니다.

### 수동 확인 항목

로컬 Chromium에서 메인의 학교급별 진입, 영역 소개 탭의 클릭·방향키·Home 키, 질문 펼침, 중학생용 응답·새로고침·이어하기·검토·수정·완료, 고등학생용 모바일 너비의 응답·검토·완료를 확인했습니다. 320·390·900·1440px 프레임에서 가로 넘침이 없고 기관 예시 테마가 적용되는 것을 확인했습니다. 데스크톱 전체 화면은 `previews/main-desktop.jpg`에 기록했습니다.

글씨·간격 개선 후 320px 프레임의 모든 주요 화면과 다시 시작 팝업을 확인하고, 390px에서 고등학생용 완료까지 재검증했습니다. 1440px에서는 검사 안내·문항·완료 정렬, 900px에서는 기관 테마의 메인·결과지 구성·기관 도입을 확인했습니다.

실제 휴대전화, 다른 브라우저, 공개 배포 주소에서의 검증은 별도입니다. 배포 환경에서는 다음 항목을 확인합니다.

- **화면 크기:** 데스크톱 폭 1440px, 모바일 폭 390px에서 가로 넘침·잘린 문구·가려진 버튼이 없는지 확인합니다.
- **검사 흐름:** 중·고등학생용 각각 선택 → 안내 → 응답 → 검토·수정 → 완료가 이어지고, 미응답 상태에서 완료할 수 없는지 확인합니다.
- **복원과 이동 기록:** 일부 응답 후 새로고침·이어하기를 하고, 다른 학교급으로 전환한 뒤 브라우저 뒤로·앞으로 가기로 기존 학교급과 답변이 복원되는지 확인합니다.
- **기관 예시와 저장:** `?org=sample`의 브랜딩과 별도 진행 상태를 확인하고, 저장을 거부한 환경에서는 저장 한계 안내가 보이는지 확인합니다.
- **키보드:** 탭 이동, 라디오 선택, 이전·다음 버튼, 응답 수정 후의 초점과 결과 화면 이동을 확인합니다.
